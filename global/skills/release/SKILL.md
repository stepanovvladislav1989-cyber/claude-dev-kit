# release — проверка перед тем, как отдать систему людям

Запускается, когда все задачи релиза (поле «Релиз» в задачах) — «готово». Работай самостоятельно, останавливайся по стоп-листу.

## 1. Проверки

1. **Безопасность кода** — субагент `reviewer` с заданием «проверь безопасность всего кода релиза» и файлом изменений: `python scripts/review_diff.py release-(N-1)` (первый релиз — `--all`, весь код) → передай путь `exports/review.diff`, сам файл не читай; в задании укажи: «файла задачи нет, рамки не проверяй — только безопасность»: утечки паролей, дыры в правах доступа, подстановка чужих команд в запросы к базе, ошибки, раскрывающие данные.
2. **Уязвимости библиотек** — `pip-audit` (или аналог стека). Не установлен — стоп-лист п. 3: предложи подключить с точной версией.
3. **Скорость и объём** — сквозные тесты на цифры из раздела «Объём, скорость, одновременная работа» в `requirements.md` есть и зелёные. Нет — добавь задачу.
4. **Одновременная работа** — если по требованиям работают больше одного человека: тест «двое меняют одну запись в одну секунду» — ни одна правка не теряется молча (вторая получает понятный отказ или обе применяются по правилу).
5. **Права доступа** — у каждого ПР о правах есть тест (`check_docs.py` предупреждает о ПР без теста).
6. **Восстановление из бэкапа** — если есть база: команда «проверка восстановления» из `CLAUDE.md` проекта (её создаёт `design`). Рабочую базу не трогать, разовые команды не набирать. Бэкап, из которого не восстановились, бэкапом не считается.
7. `python scripts/validate.py` → ПРОШЛО.

Найденное исправляется обычными задачами (`slice` на одну задачу → `ticket`), не в этом скилле.

## 2. Слепая приёмка

Один раз перед релизом, после проверок п. 1 — проверка агентом, который не видел разработки.

1. Собери номера ТР релиза: ТР из поля «Требования» задач этого релиза (статус ТР «открыто»).
2. Запусти субагента `acceptor` (Opus, модель не понижать). В задании — **только** номер релиза и список номеров ТР. Не передавай тексты задач, план, пересказ работы, пути к коду: он читает сам и только то, что разрешено его правилами.
3. Ответ приёмщика сверь с файлом `docs/acceptance/release-N.md` (число «X из Y» в первой строке, блок «Не подтверждено и не удалось проверить»). Сам отчёт не переписывай — только дописывай в блоке «что дальше»:
   - «❌ не подтверждено» → задача на исправление (`slice` на одну задачу → `ticket`): сценарий из проверки приёмщика переносится в тест задачи в `tests/acceptance` (до метки `tests/blind/release-N/` в `validate` не входит), и «готово» по задаче — только когда ещё и `python -m pytest tests/blind/release-N` зелёный по этому ТР;
   - «⚪ неясно, что считать выполнением» → вопрос пользователю (меняется ТР — стоп-лист п. 1);
   - «⚪ нет примера в эталоне» → попросить у пользователя случай для эталона.
4. Пока блок не пуст, итог приёмки — 🟡, слово «готово» о релизе запрещено. После исправлений — новая приёмка новым субагентом (чистая память), отчёт пишется заново; прежний остаётся в истории git.
5. Отчёт и проверки приёмщика — в коммит (`test: слепая приёмка релиза N`). До метки release-N проверки `tests/blind/release-N/` не входят в `validate`, поэтому «❌» не останавливает задачи на исправление.

## 3. Отчёт

По формату глобальных правил: 🟢 — все проверки пройдены и приёмка «Y из Y», 🟡/🔴 — что не прошло, чем грозит, какие задачи добавлены. В строке проверок — «слепая приёмка X из Y» и ссылка на `docs/acceptance/release-N.md`. Предложи пользователю ручную приёмку релиза на реальных данных.

## 4. Релиз принят

Только по словам пользователя «релиз принят» — он говорит их после ручной приёмки (и параллельной работы, если заменяем старую систему): сначала `python -m pytest tests/blind/release-N` — зелёный (красный — метку не ставить: после неё проверка станет красной во всех следующих задачах; сообщи пользователю), затем метка `git tag release-N` и `git push --tags`, затем `python scripts/roadmap.py` и коммит дорожной карты. С меткой проверки `tests/blind/release-N/` входят в `validate` и защищены, как `tests/acceptance` (`scripts/work_state.py`): новые файлы — свободно, правка существующих — только с разрешения пользователя.
