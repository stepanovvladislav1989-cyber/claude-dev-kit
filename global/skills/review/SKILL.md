# review — свежий взгляд перед коммитом

## 1. Субагент reviewer

Запусти субагента **reviewer** (файл `~/.claude/agents/reviewer.md`) **не в фоне** — дождись его ответа. У него права только на чтение, и он не видел процесса работы — в этом смысл ревью.

Сам собери и передай ему в задании:
- путь к файлу задачи (на этапе `design`, когда задач ещё нет, — пути к `docs/design.md` и `docs/rules.md`);
- вывод `git status` (список изменённых файлов);
- вывод `git diff` (все незакоммиченные изменения, включая новые файлы — для них `git diff --no-index /dev/null <файл>` или содержимое файла).

Ничего не отбирай и не сокращай сам: ревьюер должен видеть все изменения.

**Режим «план»** (шаг «Проверка плана» скилла `ticket`, кода ещё нет): передай путь к файлу задачи, список файлов тестов задачи и слова «проверь план». Отметку ревью после него не ставь — она нужна только после ревью кода.

## 2. После ревью

- «Критично» — исправить. Если исправление попадает в стоп-лист — сначала спросить.
- После исправлений — снова `python scripts/validate.py` до ПРОШЛО, затем **снова reviewer** с полным diff: он должен увидеть и исправления.
- Итоговый отчёт пользователю — по формату и цвету из глобальных правил. «Как считается» берётся из ответа ревьюера без изменений.
- **Отметка ревью** ставится сама: замок (`scripts/mark_reviewed.py`) записывает её, когда reviewer ответил строкой «ИТОГО» с «критично 0». Руками — только если пользователь сам принял оставшееся «критично» (спроси блоком «Нужно от меня:»): `python scripts/mark_reviewed.py --user-approved`, Claude Code спросит его разрешение; отчёт — 🟡 с этим замечанием в рисках. Без отметки замок `stop_red` не даёт завершить задачу, а проверка перед коммитом — закоммитить код. Изменишь код или тесты после отметки — она устареет, нужен новый ответ reviewer (правка документов её не сбивает).
