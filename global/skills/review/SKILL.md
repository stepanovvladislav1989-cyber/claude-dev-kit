# review — свежий взгляд перед коммитом

## 1. Субагент reviewer

Запусти субагента **reviewer** (файл `~/.claude/agents/reviewer.md`). У него права только на чтение, и он не видел процесса работы — в этом смысл ревью.

Сам собери и передай ему в задании:
- путь к файлу задачи;
- вывод `git status` (список изменённых файлов);
- вывод `git diff` (все незакоммиченные изменения, включая новые файлы — для них `git diff --no-index /dev/null <файл>` или содержимое файла).

Ничего не отбирай и не сокращай сам: ревьюер должен видеть все изменения.

**Режим «план»** (шаг «Проверка плана» скилла `ticket`, кода ещё нет): передай путь к файлу задачи, список файлов тестов задачи и слова «проверь план». Отметку ревью после него не ставь — она нужна только после ревью кода.

## 2. После ревью

- «Критично» — исправить. Если исправление попадает в стоп-лист — сначала спросить.
- После исправлений — снова `python scripts/validate.py` до ПРОШЛО.
- Итоговый отчёт пользователю — по формату из глобальных правил. Остались «важно» — это 🟡. «Как считается» берётся из ответа ревьюера без изменений. Код в отчёт не включай. Неисправленные замечания — в раздел «Риски».
- Если ревьюер не запускался — так и напиши в строке «Ревью». Пропуск ревью не скрывать.
- **Перед коммитом:** `python scripts/mark_reviewed.py` — отметка для замка `stop_red`, что ревью подтверждено для текущих изменений. Без неё завершить задачу и закоммитить код нельзя технически, не только по правилу. Изменишь код или тесты после отметки — она устареет, запусти ревью и отметку снова (правка документов её не сбивает).
