# ticket — одна задача от плана до коммита

Режимы: **старт** (по умолчанию; «следующий» — ближайшая задача по порядку и зависимостям), **продолжить**, **пауза**.

Работай самостоятельно. Останавливайся только по стоп-листу. Модели назначай по разделу «Выбор модели» глобальных правил.

## Старт

1. **Готовность.** Прочитай файл задачи, в том числе раздел «Мои тесты до сессии». Сценарии не утверждены → стоп (стоп-лист): предложи утвердить пакетом сценарии ближайших задач.
2. **План** (ты, Opus). Прочитай только связанные ПР/ТР и нужные файлы кода. Запиши в файл задачи: шаги, затрагиваемые файлы, **исполнителя кода** — `implementer` (Sonnet) или ты сам (Opus) — и причину выбора. Статус → «в работе». Одобрения не жди.
3. **Падающие тесты** (ты, Opus). **Тесты пользователя, написанные до сессии, — включи как есть**: файлы не меняй; если он написал словами — переведи в тесты `tests/acceptance/` дословно по смыслу. Утверждённые сценарии → новые тесты в `tests/acceptance/`. Если у задачи есть видимый результат (отчёт, экран, выгрузка) — сквозной тест в `tests/e2e/`. Свои крайние случаи → `tests/agent/`. В имени — номер правила или задачи (`test_pr07_…`). Есть расчёт — сверка с эталоном. Запусти: тесты должны упасть. Код в `src/` не трогай.
4. **Код** — назначенный исполнитель:
   - `implementer`: передай путь к файлу задачи и список тестов. Он работает по плану и возвращает вердикт.
   - ты сам: по плану, по шагу, после шага — связанные тесты.
   - Правила для любого исполнителя: база — через команду «бэкап + миграция»; тесты пользователя не подгонять (считаешь тест неверным — стоп-лист).
5. **Проверка** — запусти `python scripts/validate.py` сам, не полагайся на слова исполнителя.
   - НЕ ПРОШЛО у `implementer` → верни ему вывод проверки. Второй раз НЕ ПРОШЛО или он вернул проблему → забери задачу себе (Opus) и отметь в файле задачи почему.
6. **Ревью субагентом — обязательно после каждой задачи, без исключений.** Скилл `review` запускает `reviewer` (Opus, только чтение). Без ревью задача не может быть 🟢.
7. **Исправление замечаний** — тем же исполнителем, что писал код; затем снова шаг 5.
8. **Документы.** Обнови затронутые. Заполни «Итог сессии» по формату из шаблона задачи (что сделано, проверки с числами, кто писал код, ключевые строки), статус «готово». Пересобери дорожную карту: `python scripts/roadmap.py`.
9. **Отметка ревью.** `python scripts/mark_reviewed.py` — только когда критичных замечаний не осталось. Без неё замок `stop_red` не даст закончить работу, даже если проверка ПРОШЛО.
10. **Коммит.** Только после последнего `validate` с ПРОШЛО (логика и e2e зелёные) и без критичных замечаний → коммит и `git push` сам; перед коммитом pre-commit прогонит проверку ещё раз. **Одна задача — один коммит**, номер задачи в сообщении (`feat: … (Т-012)`). Иначе — без коммита, отчёт 🟡/🔴.
11. **Выгрузка кода.** Запусти `python scripts/export_ticket.py Т-012` (без коммита — без номера задачи). Путь к файлу — в отчёт.
12. **Отчёт** — по формату из глобальных правил. Последней строкой: «Дальше: `/clear`, затем `/ticket следующий`».

## Выборочная проверка (каждая 5-я готовая задача)

Если после этой задачи число задач со статусом «готово» делится на 5 — добавь к отчёту блок «Выборочная проверка»: случайно выбери одну ранее закрытую 🟢-задачу и дай по ней полный отчёт (как 🟡), с ключевыми строками. Выбор — действительно случайный, не самый удачный.

## Пауза (только по прямой команде пользователя или при заканчивающемся контексте — с сообщением ему)

- В файле задачи — «Где остановились»: что сделано, следующий шаг, кто исполнитель, открытые вопросы, какие тесты красные.
- Создай `.claude/PAUSE`, статус «пауза». Без коммита, если проверка красная. Пересобери дорожную карту.
- Выгрузи код: `python scripts/export_ticket.py` (незакоммиченные изменения) — путь сообщи пользователю.
- Создавать `.claude/PAUSE`, чтобы обойти проверку, запрещено.

## Продолжить

- Удали `.claude/PAUSE`. Прочитай «Где остановились» и `git status`. Продолжи с указанного шага.
