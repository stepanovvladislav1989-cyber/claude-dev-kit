# design — как устроено и как проверяется

Итог: `docs/design.md`, утверждённые правила в `docs/rules.md`, эталон в `tests/golden/`, настроенный `scripts/validate.py`. Кода приложения нет.

## 1. Стек

- Предложи 2–3 варианта простыми словами: что даёт, чем рискуем, насколько сложно сопровождать одному человеку. Рекомендуй самый простой подходящий.
- Решает пользователь. Запиши решение в `decisions.md` (Р) и таблицу стека в `design.md`.
- **Docker** (программа, которая запускает базу или приложение в отдельной «коробке») — только если без него не обойтись: например, PostgreSQL на компьютере пользователя или на сервере. Для SQLite и простой программы не нужен. Нужен — предложи его как часть варианта стека выше.
- Если для выбранной технологии есть готовые наборы лучших практик (skills) — предложи подключить, не подключай молча.

## 2. Устройство

- Разложи систему на три слоя: данные, расчёты, интерфейс. **Правила из rules.md живут в слое расчётов и тестируются без экранов.**
- Модель данных — диаграммой Mermaid (диаграмма текстом) + смысл таблиц и полей простыми словами.
- Если есть база данных — раздел «Надёжность»: транзакции «всё или ничего», ограничения в базе, нумерованные миграции (применённую не правим), бэкап перед миграцией, повторная загрузка без дублей. Создай одну команду «бэкап + миграция» и впиши её в `CLAUDE.md` проекта.
- Все изменения базы — файлами в `migrations/` (нумерованные, `001_…sql` или файлы инструмента миграций выбранного стека). Разовые команды, меняющие данные, запрещены правилами и замком `guard`.

## 3. Правила и инварианты

- Пройди с пользователем каждое ПР: формулировка, пример на цифрах, статус «утверждено». Утверждает только пользователь.
- Предложи инварианты (ИНВ) — соотношения, которые верны всегда. Пользователь выбирает.

## 4. Эталон

- Спроси источник заранее известных правильных ответов (закрытые периоды старой системы, ручной расчёт, выгрузка).
- Положи данные в `tests/golden/`, заполни `README.md` эталона. Реальные персональные и коммерческие данные — обезличить по решению пользователя.
- Тесты сверки с эталоном пишутся в первой задаче, где появляется расчёт, — не сейчас (красные тесты не коммитятся).

## 5. Единая проверка

- Настрой список `CHECKS` в `scripts/validate.py` под стек: тесты логики, сквозные тесты `tests/e2e/` (для интерфейса — инструмент проверки экранов выбранного стека), при необходимости линтер. Для пользователя — всё равно одна команда и один вердикт.
- Настрой проверку на GitHub (`.github/workflows/validate.yml`) под стек: те же проверки, что в `validate.py`. Если есть база данных — подними в ней тестовую базу.
- Зафиксируй точные версии всех библиотек (`requirements.txt` или файл фиксации версий выбранного стека).
- Впиши команды запуска в `CLAUDE.md` и `README.md`.
- `python scripts/validate.py` → ПРОШЛО. Предложи коммит `docs: устройство и правила`.

## Отчёт

По шаблону из глобальных правил + какие решения приняты (Р). Следующий шаг: `slice`.
