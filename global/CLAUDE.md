# Общие правила для всех моих проектов

## Кто я

Доменный эксперт и заказчик, не программист. Код не читаю — проверяю результат: тесты, сверку с эталоном, отчёты. Разрабатываю один. Язык общения — русский.

**Моё внимание — главный ограниченный ресурс.** Не спрашивай того, что можно решить по правилам ниже. Останавливайся только по стоп-листу.

## Как со мной общаться (всегда)

1. **Итог первой строкой.**
2. **Простой язык.** Английский термин при первом упоминании — с объяснением в скобках.
3. **Без кода в сообщениях и отчётах,** если я не прошу. Код и изменения (diff) смотрю сам или запрашиваю отдельно.
4. **Ошибки — через последствия:** что сломалось, чем грозит данным, что предлагаешь.
5. **Проверки — в номерах правил и цифрах,** не в названиях тестов.
6. **Вопросы по одному,** с рекомендуемым ответом. Можно предлагать сразу пакет рекомендаций, чтобы я ответил «согласен со всеми, кроме …».
7. **Решения, которые должен принять я,** — отдельным блоком.
8. **Кратко.** Подробности — по запросу.

## Стоп-лист: когда останавливаться и спрашивать

Только в этих случаях. В остальных — работай сам.

1. Меняется правило (ПР) или требование (ТР).
2. Первая схема базы данных или удаление данных.
3. Новая библиотека или программа (например, Docker).
4. Нужно выйти за рамки задачи.
5. Нужно изменить существующий тест из tests/acceptance, tests/e2e или эталон.
6. Сценарий противоречит правилу.
7. Замок `stop_red` отпустил после неудачных попыток пройти проверку.
8. Сценарии задачи ещё не утверждены.

## Анонс задачи — после плана, до тестов и кода

Коротко, без кода и терминов, не дожидаясь ответа:
```
▶ Т-003 — <название>
Что изменится для вас: 1–2 фразы — что вы сможете сделать или увидеть после задачи.
Как проверю: 2–4 проверки словами («при таких данных → такой результат»), включая что система должна отклонить.
Сложность: низкая/обычная/высокая · 💰 да/нет · код пишет: Haiku/Sonnet/Opus — почему одной фразой.
Допущения: что неясно и какой простой вариант выбран (если есть).
```

## Отчёт — светофор

**🟢 Всё хорошо — два предложения:**
```
🟢 Т-003 готово: <что изменилось для пользователя одной фразой>.
Проверки ПРОШЛО: логика 23 из 23, e2e 3 из 3, ревью без замечаний, код — Sonnet, коммит отправлен.
```
Для 💰-задачи — ещё «Как считается» из ответа ревьюера: формула словами; что при нуле/пусто/минусе.
Были допущения (см. «Как работаем») — строка «Допущения: …».

Неисправленные «мелочи» ревью — 🟢 остаётся, в строке проверок «мелочей N, не исправлены».

**🟡 Остались неисправленные «критично» или «важно» или 🔴 нужно решение** — полный отчёт:
```
🟡/🔴 Т-… — название
Что сделано: 2–4 пункта
Проверки: ПРОШЛО/НЕ ПРОШЛО · логика X из Y · e2e X из Y · эталон · инварианты · код — Haiku/Sonnet/Opus (передача выше — почему)
Ревью: найдено N · исправлено N · осталось N
Как считается (для 💰) · Допущения
Что изменено: N файлов, все в рамках задачи (или: вне — какой и почему)
Нужно от меня: …
Риски: … (в том числе неисправленные замечания ревью)
```

Строка «ревью без замечаний» или «Ревью: …» обязательна. Ревью не запускалось — только 🟡 с прямым указанием.

## Выбор модели — назначаешь сам

Правило: **сильная модель — там, где решается «что делать» и «правильно ли сделано»; более дешёвая — там, где пишется код по готовому плану.** Сами назначения делаешь ты, пользователь модели не переключает.

Сложность задачи ставится при нарезке (`slice`) в поле «Сложность» файла задачи и уточняется при плане:
- **низкая** — механика без логики: тексты, подписи, перенос по готовому образцу, 1–2 файла;
- **обычная** — новая логика по готовому плану, до ~5 файлов;
- **высокая** — устройство, несколько слоёв сразу, неясное место в плане, задача однажды уже проваливалась; всегда — задача-«скелет», схема базы и миграции.

| Работа | Кто выполняет | Модель |
|---|---|---|
| Допрос, требования, устройство, нарезка, план задачи, тесты, итоговый отчёт | Основной агент | Opus (основная сессия) |
| Код — сложность низкая, не 💰 | Субагент `implementer` с явным `model: haiku` | Haiku |
| Код — сложность обычная, не 💰 | Субагент `implementer` | Sonnet |
| Код — 💰-задача или сложность высокая | Основной агент | Opus |
| Код — `implementer` дважды вернул НЕ ПРОШЛО, или статус «застрял» / «не хватает сведений» | Модель на ступень выше: Haiku → Sonnet → основной агент Opus | — |
| Проверка плана до кода (💰 и «скелет»), ревью — всегда | Субагент `reviewer` | Opus |

- Повышать модель можно всегда, понижать для плана, тестов и ревью — никогда.
- Модель исполнителя указывай явно при каждом вызове. Таблицу держит замок `model_router` проекта.
- «Готово с сомнениями» — сомнения передай ревьюеру, повышать модель не нужно.
- Основная сессия должна работать на Opus. Если это не так — первой строкой скажи мне: «Переключите основную модель: `/model opus`».
- Какая модель писала код — укажи в отчёте.

## Где что определено

Этот файл — источник для правил общения, стоп-листа, анонса и формата отчёта, выбора модели и правил работы. Шаги задачи, пауза и выборочная проверка — скилл `ticket`. Запуск ревью и отметка ревью — скилл `review`; что проверяет ревью — агент `reviewer`. Правила исполнителя кода — агент `implementer`. Допрос — скилл `new-project`. Устройство, стек и надёжность — скилл `design`. Признаки сложности — этот файл, «Выбор модели»; нарезка, сценарии и проставление сложности — скилл `slice`. Проверка и перевод ошибок — скилл `validate`. Форматы ТР, ПР, ИНВ, Р и задачи — шаблоны в `docs/` проекта. Скрипты проекта — `scripts/`, назначение — в их файлах. Поведение замков — их файлы. Не повторяй эти правила в других местах — ссылайся.

## Как работаем

- Порядок: `new-project` → `design` → `slice` (с черновиками сценариев) → `ticket` на каждую задачу → `review` внутри. Проверка — `validate`.
- **Простота важнее всего.** Самое простое стандартное решение. Усложнение — только по стоп-листу.
- **Один факт — одно место.** Факт меняется в своём документе, в остальных — ссылка по номеру (ТР, ПР, ИНВ, Т, Р).
- **Документы до кода.** Задача не готова, пока не обновлены документы.
- **Сначала падающий тест, потом код.** Тесты пишет агент (как — скилл `ticket`); код в src/ на этом шаге не трогать.
- **Утверждённые сценарии = утверждённые тесты.** Новые тесты по ним создавай сам. Существующие тесты из tests/acceptance, tests/e2e и эталон меняются только с моего разрешения.
- **Только в рамках задачи.**
- **Неоднозначность вне стоп-листа — не выбирай молча:** бери самый простой вариант и запиши допущение в файл задачи и в отчёт («Допущения: …»).
- **Не знаешь причину падения — не правь наугад.** Сначала причина, потом одна гипотеза и одна правка; три неудачные гипотезы подряд — стоп: исполнитель возвращает «застрял», и основной агент повышает модель по таблице выше; если код уже пишет Opus — причину в отчёт 🟡 (дальше держит замок `stop_red`).
- **«Готово» = `python scripts/validate.py` показал ПРОШЛО (логика и e2e зелёные) и субагент `reviewer` проверил изменения.** Числа тестов в отчёте — из вывода `validate`, не пересказом. Ревью — после каждой задачи, без исключений.
- **Коммит и отправка на GitHub — автоматически,** если проверка ПРОШЛО и у ревьюера нет критичных замечаний (отчёт 🟡 из-за оставшихся «важно» — тоже с коммитом). Иначе — без коммита, отчёт 🟡/🔴. Сообщение: префикс (`feat:` новое, `fix:` исправление, `docs:` документы, `test:` тесты, `refactor:` переделка) + описание по-русски + номер задачи.
- **Большие документы (ТЗ) не загружай целиком** — оглавление, потом нужный раздел.
- **Если есть база данных:** связанные изменения — одной транзакцией; правила — ограничениями в базе, где возможно; миграция — только после бэкапа; повторная загрузка без дублей.
- **Изменения базы — только файлом миграции в проекте** (`migrations/`), запуск — командой «бэкап + миграция». Никаких разовых команд в терминале, которые меняют данные или структуру (`UPDATE`, `DELETE`, `INSERT`, `ALTER`, `CREATE`, `DROP`, `TRUNCATE`): они не попадают в историю, ревью и выгрузку. Читать данные запросами можно. Разовая правка данных — тоже файлом миграции.
- **Деньги** — Decimal/NUMERIC, не float.
- **Библиотеки — с точной версией.** Новая — по стоп-листу; обновление — отдельной задачей.
- **Проверку перед коммитом не обходить.**
- **Контекст заканчивается** — сохрани прогресс (`ticket`, режим «пауза») и скажи мне одной строкой.
