# Общие правила для всех моих проектов

## Кто я

Доменный эксперт и заказчик, не программист. Код не читаю — проверяю результат: тесты, сверку с эталоном, отчёты. Разрабатываю один. Язык общения — русский.

**Моё внимание — главный ограниченный ресурс.** Не спрашивай того, что можно решить по правилам ниже. Останавливайся только по стоп-листу.

## Как со мной общаться (всегда)

1. **Итог первой строкой.**
2. **Простой язык.** Английский термин при первом упоминании — с объяснением в скобках.
3. **Без кода в сообщениях,** если я не прошу. Исключение — «Ключевые строки» в отчёте после каждой задачи.
4. **Ошибки — через последствия:** что сломалось, чем грозит данным, что предлагаешь.
5. **Проверки — в номерах правил и цифрах,** не в названиях тестов.
6. **Вопросы по одному,** с рекомендуемым ответом. Можно предлагать сразу пакет рекомендаций, чтобы я ответил «согласен со всеми, кроме …».
7. **Решения, которые должен принять я,** — отдельным блоком.
8. **Кратко.** Подробности — по запросу.

## Стоп-лист: когда останавливаться и спрашивать

Только в этих случаях. В остальных — работай сам.

1. Меняется правило (ПР) или требование (ТР).
2. Первая схема базы данных или удаление данных.
3. Новая библиотека.
4. Нужно выйти за рамки задачи.
5. Нужно изменить существующий тест из tests/acceptance или эталон.
6. Сценарий противоречит правилу.
7. Замок `stop_red` отпустил после неудачных попыток пройти проверку.
8. Сценарии задачи ещё не утверждены.

## Отчёт — светофор

**Каждый отчёт заканчивается аудитом кода — блоком «Ключевые строки»** из ответа субагента `reviewer`, без изменений. Что отбирать, сколько строк и формат комментариев задаёт `~/.claude/agents/reviewer.md`.

**🟢 Всё хорошо — два предложения, затем ключевые строки:**
```
🟢 Т-003 готово: <что изменилось для пользователя одной фразой>.
Проверки ПРОШЛО: логика 23 из 23, e2e 3 из 3, ревью без замечаний, код — Sonnet, коммит отправлен.
Весь код задачи: exports/Т-003.md
```
Для 💰-задачи перед ключевыми строками — ещё «Как считается»: формула словами; что при нуле/пусто/минусе.

**🟡 Есть неисправленные замечания или 🔴 нужно решение** — полный отчёт:
```
🟡/🔴 Т-… — название
Что сделано: 2–4 пункта
Проверки: ПРОШЛО/НЕ ПРОШЛО · логика X из Y · e2e X из Y · эталон · инварианты · код — Sonnet/Opus (передача Opus — почему)
Ревью: найдено N · исправлено N · осталось N
Как считается (для 💰) · Ключевые строки
Что изменено: N файлов, все в рамках задачи (или: вне — какой и почему)
Нужно от меня: …
Риски: …
Весь код задачи: exports/Т-….md
```

Строка «ревью без замечаний» или «Ревью: …» обязательна. Ревью не запускалось — только 🟡 с прямым указанием.

## Выбор модели — назначаешь сам

Правило: **сильная модель — там, где решается «что делать» и «правильно ли сделано»; более дешёвая — там, где пишется код по готовому плану.** Сами назначения делаешь ты, пользователь модели не переключает.

| Работа | Кто выполняет | Модель |
|---|---|---|
| Допрос, требования, устройство, нарезка, план задачи, тесты, итоговый отчёт | Основной агент | Opus (основная сессия) |
| Код по плану — обычная задача | Субагент `implementer` | Sonnet |
| Код — 💰-задача, первая задача-«скелет», схема базы или миграции | Основной агент | Opus |
| Код — `implementer` дважды вернул НЕ ПРОШЛО или проблему | Основной агент забирает задачу | Opus |
| Ревью — всегда | Субагент `reviewer` | Opus |

- Повышать модель можно всегда, понижать для плана, тестов и ревью — никогда.
- Основная сессия должна работать на Opus. Если это не так — первой строкой скажи мне: «Переключите основную модель: `/model opus`».
- Какая модель писала код — укажи в отчёте.

## Где что определено

Этот файл — источник для правил общения, стоп-листа, формата отчёта, выбора модели и правил работы. Шаги задачи и выборочная проверка — скилл `ticket`. Ключевые строки — агент `reviewer`. Правила исполнителя кода — агент `implementer`. Допрос — скилл `new-project`. Нарезка и сценарии — скилл `slice`. Устройство и надёжность — скилл `design`. Поведение замков — их файлы. Не повторяй эти правила в других местах — ссылайся.

## Как работаем

- Порядок: `new-project` → `design` → `slice` (с черновиками сценариев) → `ticket` на каждую задачу → `review` внутри. Проверка — `validate`.
- **Простота важнее всего.** Самое простое стандартное решение. Усложнение — только по стоп-листу.
- **Один факт — одно место.** Факт меняется в своём документе, в остальных — ссылка по номеру (ТР, ПР, ИНВ, Т, Р).
- **Документы до кода.** Задача не готова, пока не обновлены документы.
- **Сначала падающий тест, потом код.** На этом шаге код в src/ не трогать.
- **Утверждённые сценарии = утверждённые тесты.** Новые тесты по ним создавай сам. Существующие тесты из tests/acceptance и эталон меняются только с моего разрешения.
- **Только в рамках задачи.**
- **«Готово» = `python scripts/validate.py` показал ПРОШЛО (логика и e2e зелёные) и субагент `reviewer` проверил изменения.** Числа тестов в отчёте — из вывода `validate`, не пересказом. Ревью — после каждой задачи, без исключений.
- **Коммит и отправка на GitHub — автоматически,** если проверка ПРОШЛО и у ревьюера нет критичных замечаний. Иначе — 🟡/🔴 без коммита. Сообщение: префикс (`feat:` новое, `fix:` исправление, `docs:` документы, `test:` тесты, `refactor:` переделка) + описание по-русски + номер задачи.
- **Большие документы (ТЗ) не загружай целиком** — оглавление, потом нужный раздел.
- **Если есть база данных:** связанные изменения — одной транзакцией; правила — ограничениями в базе, где возможно; миграция — только после бэкапа; повторная загрузка без дублей.
- **Изменения базы — только файлом миграции в проекте** (`migrations/`), запуск — командой «бэкап + миграция». Никаких разовых команд в терминале, которые меняют данные или структуру (`UPDATE`, `DELETE`, `INSERT`, `ALTER`, `CREATE`, `DROP`, `TRUNCATE`): они не попадают в историю, ревью и выгрузку. Читать данные запросами можно. Разовая правка данных — тоже файлом миграции.
- **Деньги** — Decimal/NUMERIC, не float.
- **Библиотеки — с точной версией.** Новая — по стоп-листу; обновление — отдельной задачей.
- **Проверку перед коммитом не обходить.**
- **Контекст заканчивается** — сохрани прогресс (`ticket`, режим «пауза») и скажи мне одной строкой.
