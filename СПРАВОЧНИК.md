## 1. Что это и три главных требования

Метод для одного человека: я — доменный эксперт и заказчик, не программист. Код пишет агент (Claude Code), после каждой задачи его проверяет субагент, обязательные правила держат замки. Модели по мощности агент назначает сам. Метод один для любых проектов.

1. **По-русски и понятно** — правила общения в [global/CLAUDE.md](global/CLAUDE.md).
2. **Понятно до и после задачи** — перед задачей анонс простыми словами (что изменится и как проверим), после — отчёт-светофор без кода. Код и изменения смотрю сам, когда хочу.
3. **Минимум кнопок** — я включаюсь только в важные моменты (раздел 4).

Приоритет: **простота и воспроизводимость важнее всего остального.**

## 2. Кто что делает

| Кто | Роль |
|---|---|
| **Я** | Утверждаю правила и сценарии, читаю отчёты, решаю по стоп-листу, делаю приёмку |
| **Основной агент** (Opus) | Допрос, документы, план задачи, тесты, код сложных задач, проверки, отчёт, коммит; назначает модели |
| **Субагент `implementer`** (Sonnet, для низкой сложности — Haiku) | Пишет код обычных задач строго по плану. Тесты менять не может |
| **Субагент `reviewer`** (Opus) | После **каждой** задачи проверяет все изменения свежим взглядом. Права только на чтение. В 💰-задачах и «скелете» ещё и проверяет план с тестами до кода |
| **Замки** | Автоматически блокируют опасное и не дают закончить с ошибками |
| **GitHub** | Повторяет проверку на сервере при каждой отправке кода |

Тот, кто пишет код, не проверяет его сам.

## 3. Этапы

| Этап | Скилл | Критерий выхода |
|---|---|---|
| 1. Допрос и требования | `/new-project` | Нет вопросов, меняющих устройство; я узнаю свою задачу |
| 2. Устройство, правила, эталон | `/design` | Правила утверждены, эталон лежит, проверка ПРОШЛО |
| 3. Задачи и сценарии | `/slice` | Сценарии утверждены |
| 4. Задачи по кругу | `/ticket следующий` | Проверка ПРОШЛО, ревью субагентом пройдено, коммит отправлен |
| 5. После функции | вручную | Функция пройдена руками, реальные данные сошлись |
| 5а. Перед выпуском релиза | `/release` | Безопасность, библиотеки, скорость, одновременная работа, восстановление из бэкапа — проверено |
| 6. Приёмка | вручную | Параллельная эксплуатация (если заменяем систему), внешний аудит перед запуском для других |

Шаги одной задачи — в скилле `ticket`. Главное в них: каждая задача — в новой сессии; модель выбирается на каждую задачу; анонс простыми словами с вопросом о моих проверках; тесты до кода (пишет агент); проверка плана ревьюером для 💰; журнал по ходу; поиск причины, а не правки наугад; проверка до ПРОШЛО; **ревью субагентом после каждой задачи без исключений**; автокоммит; отчёт по формату из [global/CLAUDE.md](global/CLAUDE.md).

### Модели по мощности

Агент назначает модели сам, я их не переключаю. Принцип: **сильная модель решает «что делать» и «правильно ли сделано», более дешёвая пишет код по готовому плану.** Хороший план и сильное ревью позволяют дешёвому исполнителю давать то же качество при заметно меньшем расходе лимитов. Сложность задачи (низкая / обычная / высокая) ставится при нарезке; 💰-задачи, высокая сложность и неудачи исполнителя переходят на сильную модель. Замок `model_router` не даёт понизить модель против таблицы. Таблица назначений — в [global/CLAUDE.md](global/CLAUDE.md), раздел «Выбор модели». Используются только модели Claude — код и данные не уходят сторонним провайдерам.

## 4. Где я включаюсь и нажимаю кнопки

- **Старт проекта:** отвечаю на вопросы, правлю черновики агента.
- **Правила и сценарии:** утверждаю пакетами на свежую голову — главная точка внимания.
- **Анонс перед задачей:** читаю, что изменится, как проверим и какая модель; отвечаю «нет» или своей проверкой.
- **Отчёт после задачи:** читаю итог.
- **Стоп-лист:** решаю, когда агент остановился (перечень — в [global/CLAUDE.md](global/CLAUDE.md)).
- **Мои существующие тесты и эталон:** разрешаю или запрещаю изменение — Claude Code сам покажет запрос.
- **Приёмка:** ручная проверка функций, сверка реальных данных, параллельная эксплуатация.

Всё остальное — без меня: обычные команды разрешены заранее, коммит и отправка автоматические, опасное блокирует замок. Что делать в каждой ситуации — [ШПАРГАЛКА.md](ШПАРГАЛКА.md).

## 5. Почему можно не читать весь код — система контролей

| Контроль в учёте | В разработке |
|---|---|
| Сверка с 1С | Сверка с эталоном (`tests/golden`) |
| «Актив = пассив» | Инварианты (ИНВ) в тестах |
| Четыре глаза | Код пишет агент, проверяет субагент `reviewer` |
| Выборочная проверка | Периодический полный разбор случайной задачи |
| Права доступа | Замки на пароли, опасные команды, мои тесты |
| Журнал проводок | Git: история с откатом |
| Двойной контроль | Проверка на компьютере (pre-commit) и на GitHub (CI) |
| Параллельный учёт | Параллельная эксплуатация при приёмке |

Код в отчёты не попадает. Когда хочу посмотреть — вкладка **Source Control** в VS Code или выгрузка задачи по просьбе в один файл `exports/Т-….md` (новые файлы целиком, изменённые — «было → стало»). Как пользоваться — [ШПАРГАЛКА.md](ШПАРГАЛКА.md), раздел «Разбор кода — когда сам захочу».

Большое исходное ТЗ агенту целиком не даётся: из него по разделам выписываются ТР и ПР со ссылкой «Источник: ТЗ п. …».

## 7. Надёжность

**ACID** — четыре гарантии базы данных:

| | Что значит | Аналогия |
|---|---|---|
| A — атомарность | Операция целиком или никак | Проводка не запишет дебет без кредита |
| C — согласованность | База не пускает данные против правил | 1С не проведёт документ без контрагента |
| I — изолированность | Одновременная работа не портит данные | Закрытый период |
| D — долговечность | Подтверждённое не пропадает | Проведённый документ после отключения света |

**Изменения базы — только файлом миграции** (`migrations/`). Разовые команды в терминале, меняющие данные, не попадают в историю, ревью и выгрузку — поэтому запрещены правилом и замком `guard`. Так всё, что меняет данные, видно в коде и проходит проверку.

Как это закладывается (транзакции, бэкап перед миграцией, повторная загрузка без дублей, деньги не во float, точные версии библиотек, проверка на GitHub) — в скилле `design` и правилах работы [global/CLAUDE.md](global/CLAUDE.md).

## 8. Замки

| Замок | Где | Что делает |
|---|---|---|
| guard | Глобально | Запрещает доступ к паролям, разрушительные команды (в том числе откат всех несохранённых изменений), обход проверки перед коммитом, изменение базы разовой командой в терминале (Bash и PowerShell) |
| protect_tests | В проекте | Новые тесты создаются сами; изменение моих существующих тестов и эталона, а также самих замков и настроек проверки — только с моего разрешения (в том числе командами Bash и PowerShell). Запоминает, что я разрешил |
| проверка по результату | В проекте (`validate`) | Если существующий тест или эталон изменён без моего разрешения — любым способом, даже в обход protect_tests — НЕ ПРОШЛО |
| model_router | В проекте | Не даёт запустить исполнителя на 💰-задаче или задаче высокой сложности, Haiku — не на низкой сложности, ревьюера — слабее Opus |
| session_context | В проекте | При старте, после `/clear` и сжатия памяти подгружает агенту журнал текущей задачи |
| stop_red | В проекте | Нельзя закончить работу с красной проверкой **или без подтверждённого ревью** (отметку ставит сам замок `scripts/mark_reviewed.py`, когда reviewer ответил без «критично»; устаревает при изменении кода и тестов; правка документов её не сбивает). Агент задал мне вопрос блоком «Нужно от меня:» — отпускает после одной проверки с пометкой «работа не готова». После нескольких неудачных попыток агента отпускают и показывают мне предупреждение. По команде «пауза» не держит. Паузу и отметку ревью агент напрямую ставит только с моего разрешения (защита от пропуска шага, не от умышленного обхода) |
| pre-commit | В проекте | Перед каждым коммитом прогоняет все тесты, e2e и проверку документов **и проверяет отметку ревью для изменённого кода**; красная проверка или нет ревью — коммита нет |
| CI | На GitHub | Та же проверка на сервере: зелёная галочка или красный крестик. Плюс: мои тесты и эталон изменены без строки «Разрешено пользователем: защищённые тесты» в коммите — красный крестик (строку пишет агент: правка становится заявленной, а не тихой) |
| тестовая база | В проекте (`tests/conftest.py`) | Тесты не запускаются, если задан адрес рабочей базы, а отдельной тестовой (со словом «test») нет |
| Dependabot | На GitHub | Предупреждает об уязвимостях в библиотеках |

Точные условия и числа — в файлах замков (раздел 0).

Замки рассчитаны на обычный режим Claude Code с запросами разрешения. В режиме без запросов (bypassPermissions) «разрешение» на правку защищённых тестов записывается само — проверка по результату в нём не защищает. Замки защищают от случайностей и спешки агента, а не от целенаправленного обхода.

**Автокоммит** — правило в [global/CLAUDE.md](global/CLAUDE.md), «Как работаем».

## 9. Ручное тестирование и приёмка

- **Не после каждой задачи** — логику проверяют тесты.
- **После каждой функции** (группы задач с видимым результатом) — 10–15 минут пройти её руками на экранах и прогнать реальные данные.
- **На приёмке** — полный проход; при замене старой системы — 1–2 периода параллельно; перед запуском для других людей — внешний аудит кода.
- Нашёл ошибку руками → не хватило сценария → сценарий добавляется в тесты.

## 10. Границы метода

- **Сильная сторона — точность правил и цифр:** правила формулирует эксперт, эталон и сверка доказывают результат.
- **Слабая — инженерия:** безопасность, одновременная работа, скорость. Закрывается простыми технологиями, узким кругом пользователей на старте, ACID, внешним аудитом.
- **Главный риск — пробелы в правилах:** где правило не записано, агент заполнит пробел уверенно и неправильно. Закрывается допросом.

**Метрики:** доля совпадений с эталоном и необъяснённые расхождения при приёмке; ошибки, найденные после «готово»; критичные замечания внешнего аудита; доля задач, которые пришлось передать на модель выше (Haiku → Sonnet → Opus) (если высокая — назначения пересмотреть).

## 11. Универсальность

От проекта к проекту меняются только стек (`design.md`), команды (`CLAUDE.md` проекта) и содержимое проверки (`scripts/validate.py`, `.github/workflows/validate.yml`). Правила живут в слое расчётов и тестируются без экранов, поэтому переживают смену интерфейса.

## 12. Донастройка

- Метод правится в источнике (раздел 0), не в копиях.
- Скиллы, агент и общие правила — в `C:\Users\ИМЯ\.claude\`, действуют сразу во всех проектах. Замки и структура — в `project-template/` репозитория `claude-dev-kit` (раздаётся архивом `project-template.zip` из Releases); в старые проекты — копировать вручную. Изменил `project-template/` → пересобери и опубликуй новый Release, иначе новые проекты получат старую версию.
- Строка в CLAUDE.md ни на что не влияет → удалить.
- Новое добавляем только по итогам уроков задач (строка «Урок задачи» в итогах): агент повторяет ошибку → тест или замок, а не абзац текста. Остальное — только исправляем то, что не работает.

## 13. Словарь

| Термин | Простыми словами |
|---|---|
| Агент | ИИ, который сам пишет код и запускает команды |
| Субагент | Отдельный агент со своей памятью и моделью; у нас — исполнитель и ревьюер |
| Opus / Sonnet / Haiku | Модели Claude: Opus — самая сильная, Sonnet — быстрее и экономнее, Haiku — самая быстрая, для механической работы |
| Скилл | Записанная инструкция для агента, вызывается командой `/имя` |
| Замок (хук) | Программа, срабатывает автоматически и блокирует или проверяет |
| CLAUDE.md | Памятка, которую агент читает в начале каждой сессии |
| Git / коммит | Журнал изменений / одна запись в нём |
| GitHub | Хранилище журнала в интернете |
| pre-commit | Проверка перед каждой записью в журнал |
| CI | Та же проверка на сервере GitHub |
| Тест | Автопроверка «при таких данных ожидаю такой результат» |
| E2E | Сквозная проверка от загрузки данных до экрана или отчёта; лежит в `tests/e2e/`, считается отдельно |
| Релиз | Часть системы, которую можно внедрить и эксплуатировать отдельно; метка в git `release-N` |
| Эталон | Данные с заранее известными правильными ответами |
| Инвариант | Соотношение, которое верно всегда |
| Миграция | Изменение структуры базы данных |
| Контекст | Рабочая память агента в одной сессии |
| Definition of Done | Список условий, без которых задача не готова |
