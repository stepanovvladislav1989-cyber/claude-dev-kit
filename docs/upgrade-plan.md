## 2. Разбор по идеям

### Идея 1. Манифест требований (прослеживаемость — по каждому требованию можно найти, где оно сделано и как проверено)

- **Что это:** пронумерованный список требований со статусами, задача без номера требования не допускается.
- **Уже есть:** ТР-01… с заголовками в `requirements.md`. Задачи ссылаются на ТР (поле «Требования»). `check_docs.py` ловит дубли и неизвестные номера, предупреждает о ТР без задачи.
- **Что изменить:**
  1. Бриф сохраняется дословно в `docs/brief.md`, а абзацы нумеруются (Б-1, Б-2…).
  2. У каждого ТР три строки: `Из брифа: «дословная цитата» (Б-3)` или `Источник: допрос, тема 4` или `Источник: ТЗ п. 2.1`; `Статус: открыто | отложено | снято — причина`.
  3. Статусы «в работе» и «сделано» вручную **не пишутся**: скрипт берёт их из задач. Иначе один и тот же факт пришлось бы держать в двух местах.
  4. `check_docs.py`: после нарезки ТР без задачи (кроме «отложено» и «снято») и задача без ТР — **ошибка**. Абзац брифа, не попавший ни в одно ТР, — предупреждение.
  5. Сверка «все номера на месте» на каждом переходе: требования → нарезка (новая ошибка выше) → задача → тест (уже есть для ПР) → приёмка (идея 5, таблица по каждому ТР).
- **Чем упрощает:** ничего из брифа не теряется. Видно, откуда взялось каждое требование.
- **Риск:** дословные цитаты из диктовки бывают корявыми. Поэтому формулировку ТР агент пишет нормально, а цитату держит рядом как доказательство.
- **Вердикт:** внедрять упрощённо. Отдельный `manifest.md` дублировал бы `requirements.md`.

### Идея 2. Допрос с рекомендованным ответом

- **Уже есть:** пачки по 5–7 вопросов с рекомендуемыми ответами, «согласен со всеми, кроме…», 10 слепых зон, простой язык, короткие сессии.
- **Что добавить:**
  1. К каждому рекомендуемому ответу — строка «почему».
  2. Обязательный проход по чек-листу идеи 3 для каждого правила с деньгами.
  3. Глубина без выбора перед стартом. Правила с деньгами, удалением и правами допрашиваются «глубоко», то есть по чек-листу. Остальное — «обычно»: вопрос задаётся, только если пробел испортит результат. «Строго» — по вашей фразе «только по брифу».
  4. Проект большой (больше ~25 задач или 3+ независимых частей) → агент предлагает разделить его на релизы и объясняет границы.
- **Чем упрощает:** не нужно выбирать глубину, вы просто отвечаете «ок».
- **Риск:** допрос по чек-листу длиннее. Смягчение: пункты, которые к проекту не относятся (например, валюта), агент отмечает «не относится» одной строкой и не спрашивает.
- **Вердикт:** внедрять упрощённо.

### Идея 3. Чек-лист нестандартных ситуаций (корнеркейсов — редких ситуаций, где программы ломаются) для финансов и учёта

Один файл, например `global/skills/new-project/corner-cases.md`. На него ссылаются допрос (вопросы), нарезка (сценарии «что отклонить») и ревьюер (что проверить). Текст хранится в одном месте.

**Ваши пункты — оставить все:**
1. Закрытый период: попытка создать, изменить или удалить документ задним числом.
2. Сторно и исправительные проводки вместо удаления: что видно в отчёте за старый и новый период.
3. Ноль, минус, очень большая сумма (переполнение, экспоненциальная запись в выгрузке).
4. Округление и копейки; валюта и курс на дату документа (пункт только для проектов с валютой).
5. Один и тот же документ дважды (повторная загрузка, двойной клик).
6. Обрыв посреди операции: остаётся «всё или ничего».
7. Права: кто видит и кто правит.
8. Откат: можно ли вернуть прежнее состояние и кто это может.
9. Отчёт за период до и после правки: какие итоги должны совпасть, какие измениться.

**Добавить:**

10. **Распределение копеек:** сумма частей равна целому (100 ₽ на 3 = 33,33 + 33,33 + 33,34). Это самая частая финансовая ошибка.
11. **Округление построчно или итогом** (НДС по строкам ≠ НДС от итога): правило выбирает заказчик.
12. **Границы периода:** последний день месяца, 29 февраля, документ в 23:59, часовой пояс.
13. **Сальдо:** остаток на начало периода = остаток на конец прошлого.
14. **Кривые данные источника:** пустые поля, чужая кодировка, дата текстом, файл оборван на середине.
15. **След изменений:** кто и когда изменил сумму, видно ли прежнее значение.

**Убрать или объединить:**
- «рост объёма» уже покрыт тремя числами допроса (объём, скорость, одновременная работа);
- «первый запуск / пустой экран» превращается в одну строку «пустая база → отчёт показывает нули, а не ошибку».

- **Вердикт:** внедрять.

### Идея 4. Нарезка на задачи и волны субагентов (субагент — отдельный экземпляр Claude с чистой памятью)

- **Уже есть:**
  - задача рассчитана на одну сессию и примерно 5 файлов;
  - план задачи содержит список файлов;
  - исполнитель `implementer` работает только с файлами из плана;
  - код пишет Haiku, Sonnet или Opus по сложности;
  - «ремонт» = повторный вызов с выводом проверки, затем модель выше; три неудачные гипотезы → «застрял».
- **Параллельность — отказаться.** Причины:
  1. В маленьком проекте у задач почти всегда общие файлы: модель данных, миграции, общие расчёты. Волн из 2+ задач почти не будет.
  2. Правила «одна задача — один коммит» и «проверка всего проекта перед завершением» с параллельными агентами ломаются: красный тест одного агента останавливает другого.
  3. Отлаживать две одновременные ошибки тяжелее, а отлаживать будете вы через отчёты.
  4. Ограничение Claude Code: субагент не может запустить своего субагента. Если задачу целиком отдать субагенту, он не сможет вызвать ревьюера.
- **«Главный агент только раздаёт» — не менять.** Сейчас основной агент сам пишет план, тесты и 💰-код. Это сознательное правило «сильная модель решает, что делать и правильно ли сделано».
- **Что добавить:** явный лимит ремонта, всего **4 попытки** на задачу. Две у назначенного исполнителя, затем модель выше, у неё ещё две. Потом стоп и отчёт 🔴 с вопросом вам. Сейчас лимит размыт между правилами.
- **Вердикт:** последовательно по умолчанию, параллельность не делать даже опцией.

### Идея 5. Независимая («слепая») приёмка (проверка агентом, который не видел разработки)

- **Уже есть:** ревьюер смотрит каждую задачу, но он видит код и задачу. Тесты-приёмки пишет основной агент из утверждённых вами сценариев. Есть эталон и ваша ручная приёмка релиза.
- **Что добавить:** шаг в скилле `release` и новый субагент `acceptor`.
  - **Получает только:** `docs/brief.md`, `docs/requirements.md`, `docs/rules.md` (ответы допроса записаны туда), `tests/golden/` и инструкцию «как запустить программу» из README. Код, задачи, журналы и тесты разработчика не получает.
  - **Делает:** по каждому ТР составляет проверку из брифа, запускает программу как пользователь (команда, выгрузка, экран) и записывает, что увидел. Свои проверки кладёт в `tests/blind/`.
  - **Выдаёт:** `docs/acceptance/release-N.md` — таблица «ТР · подтверждено / не подтверждено / не удалось проверить · что запускал · что увидел». Над таблицей отдельный список всех «не подтверждено» и «не удалось». Пока такой список не пуст, итог приёмки — не 🟢, и слово «готово» запрещено правилом агента. Каждый пункт превращается в задачу.
- **Как не проверять себя теми же глазами:**
  1. **Ваши эталонные примеры** с известным ответом — главный судья. У каждого ТР, связанного с деньгами, должен быть хотя бы один пример из эталона, иначе «не удалось проверить».
  2. Приёмщик не видит тестов разработчика, поэтому не может повторить их ошибку.
  3. Проверки идут через внешнее поведение программы, а не через внутренние функции.
  4. Ваша ручная приёмка на реальных данных остаётся последним шагом.
- **Риск:** приёмщик может «додумать» требование. Смягчение: при неясной формулировке он пишет «не удалось проверить — неясно, что считать выполнением» и не угадывает. Это и есть сигнал, что ТР сформулировано плохо.
- **Вердикт:** внедрять.

### Идея 6. Спецификация, которую реально проверить

- **Уже есть:** вы утверждаете каждое ПР с примером на цифрах. Решения записываются в `decisions.md`. `design.md` может быть длинным.
- **Что добавить:** первый раздел `design.md` — «Пересказ для заказчика», не больше страницы:
  - что будет сделано, 5–7 строк;
  - решения, принятые за вас: «выбрал X, потому что Y, альтернатива Z → Р-04»; подробности остаются в `decisions.md`, здесь только строка со ссылкой;
  - рискованные места, 2–4 строки.

  Читаете и отвечаете «ок» только по пересказу.
- **Проверка «все ТР есть в спецификации»** не нужна. Покрытие ТР проверяется на нарезке (идея 1), а архитектура не обязана упоминать каждое требование.
- **Вердикт:** внедрять упрощённо.

### Идея 7. Режимы работы

- **Ваша гипотеза подтверждается частично.**
  - «Полный автомат без вопросов» — отказаться: агент ответил бы за вас на вопросы о деньгах и правах.
  - Отдельный «ручной режим» тоже не нужен. Ручное согласование финансовой логики уже встроено: правила ПР утверждаете вы, 💰-задачи проходят проверку плана до кода, изменение ПР и ТР в стоп-листе.
  - Переключатель режимов — лишняя сущность, про которую надо помнить.
- **Вердикт:** один режим — текущий полуавтомат. Отказаться от режимов.

### Идея 8. Визуальный дашборд

- **Как сделать проще всего:**
  - Один скрипт `scripts/dashboard.py` с шаблоном внутри (без отдельного файла шаблона).
  - Он собирает `exports/dashboard.html` из того, что уже есть:

    | Что на странице | Откуда берётся |
    |---|---|
    | требования и статусы | `requirements.md` + задачи |
    | задачи по релизам | файлы задач |
    | проверка | результат последнего `validate` |
    | ревью | отметка ревью |
    | пауза | `.claude/PAUSE` |
    | события | `git log` + журнал событий |
  - Новый служебный файл только один: `exports/events.jsonl`, журнал последних событий по строке на событие. Пример строки: `{"time":"…","kind":"validate","text":"ПРОШЛО 23/23"}`.
  - Отдельный `state.json` со статусами не нужен: он дублировал бы задачи и мог бы с ними разойтись.
- **На странице:**
  - Общий цвет: синий — агент работает; оранжевый — нужен вы (последний ответ содержит «Нужно от меня:» — это уже умеет распознавать замок `stop_red`); зелёный — проверка ПРОШЛО и ревью есть; красный — проверка НЕ ПРОШЛО.
  - Полоса этапов: допрос → устройство → нарезка → задачи → приёмка → релиз. Этап определяется по заполненности документов.
  - Таблица требований со статусами.
  - Задачи **по релизам** вместо волн (волн нет, идея 4). Цвета: ожидает / в работе / на проверке / в ремонте / готово / пауза.
  - Последние 20 событий.
  - Крупный блок «Что нужно от вас» с текстом после строки «Нужно от меня:».
- **Как обновляется:** скрипт вызывают замки, которые уже есть:
  - `stop_red` в конце каждого ответа агента;
  - `session_context` при старте сессии;
  - `mark_reviewed` после ревью.

  Новых хуков не нужно. Страница сама обновляется раз в 5 секунд (одна строка в HTML).
- **Как открыть:** двойным кликом в обычном браузере. В VS Code — через расширение Live Preview (просмотр страниц прямо в редакторе); встроенный Simple Browser локальные файлы открывает ненадёжно.
- **Без сервера, без библиотек, без интернета:** оформление встроено в саму страницу.
- **Риск:** скрипт, вызываемый каждым ответом, не должен ломать работу. Поэтому любая его ошибка глушится: дашборд не обновится, но агент продолжит.
- **Вердикт:** внедрять. Один скрипт, ноль новых хуков, один служебный файл.

### Идея 9. Папка прогона

- **Уже есть:** всё перечисленное лежит в git — бриф, требования, ответы, спецификация, план, отчёты задач (итог и журнал в файле задачи), решения, метки релизов. «Через месяц понять, что и почему» = `git log` + `decisions.md` + задачи.
- Копии в `.run/дата-название/` дублировали бы `docs/` и расходились бы с ним.
- **Вердикт:** отказаться. Взять две мелочи: `docs/brief.md` (идея 1) и `docs/acceptance/release-N.md` (идея 5).

### Идея 10. Экономия токенов

- **Уже внедрено:**
  - ревьюер читает изменения из файла, а не из пересказа;
  - исполнитель получает путь к задаче, а не её текст;
  - строгие короткие форматы ответов субагентов;
  - проверка не гоняет тесты повторно без изменений;
  - модель по сложности;
  - большое ТЗ читается по оглавлению.
- **Добавить без усложнения:**
  1. Приёмщику — только 4 документа и эталон, код не читает.
  2. Дашборд агент никогда не читает и не пересказывает.
  3. Чек-лист — отдельным файлом, читается только на допросе, нарезке и ревью 💰-задач.
- Обещать «30%» не могу: замера «до/после» у комплекта нет, а основные приёмы уже работают.
- **Вердикт:** почти всё есть, три мелких дополнения войдут в шаги ниже.

## 3. Что отклоняю и почему

| Что | Почему не подходит |
|---|---|
| Параллельные субагенты | Мало выгоды в маленьких проектах; ломают «одна задача — один коммит» и проверку перед завершением; тяжелее отлаживать; субагент не может вызвать ревьюера |
| Режим «полный автомат» | Агент отвечал бы за вас на вопросы о деньгах и правах |
| Ручной режим как переключатель | Ручное согласование финансовой логики уже встроено (ПР, 💰, стоп-лист) |
| Отдельный `manifest.md` | Дублирует `requirements.md` |
| `state.json` со статусами | Дублирует файлы задач, может с ними разойтись |
| Папки прогона `.run/` | Дублируют `docs/` и git |
| Чтение кода или большой спецификации | Ни один пункт плана этого не требует: вы читаете пересказ, таблицу приёмки и дашборд |

## 6. Процесс после доработки

✋ — где вы участвуете вручную.

1. ✋ **Бриф и допрос.** Вы диктуете бриф и отвечаете «ок» или правите пачки вопросов с рекомендациями. Агент нарезает бриф на ТР с цитатами и проходит чек-лист.
2. ✋ **Устройство.** Вы читаете одностраничный пересказ, утверждаете правила ПР на цифрах и даёте эталон.
3. ✋ **Нарезка.** Вы утверждаете одним пакетом задачи, сценарии и свои проверки. Агент проверяет, что каждое ТР попало в задачу.
4. **Задачи — без ваших решений.** План → тесты → код → проверка → ревью → коммит, с отчётом-светофором. Вы смотрите дашборд и печатаете `/clear` и `/ticket следующий` (механика, не решение). Остановка — только по стоп-листу, и тогда дашборд оранжевый.
5. **Слепая приёмка и проверки релиза** — автоматически, с таблицей по каждому ТР.
6. ✋ **Приёмка релиза.** Вы проверяете на реальных данных и говорите «релиз принят».

Итого **4 ручные точки** на проект плюс остановки по стоп-листу. Цель «не больше пяти» выполнена.

Честное ограничение: `/clear` между задачами Claude Code сделать сам не может, это остаётся вашей кнопкой.
